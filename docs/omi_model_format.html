Overall Goal

We currently have a proliferation of ad-hoc standards for distributing models. This worked well for small-scale diffusion (e.g. sd1.5), but as diffusion pipelines grow in size and complexity, it has become unwieldy to handle new partial models (such as a single fine-tuned DiT or a LoRA adaptation).

The Open Model Initiative (OMI) aims to streamline how we package and share both full models and derived adapters such as LoRAs, textual inversions, etc. This document proposes:

  • A single-file distribution approach based on .safetensors with well-defined metadata.
  • A standard key-naming convention, preserving original (base) model parameter names wherever possible, so that partial adapters (e.g. LoRAs) can reliably map to them.
  • A reference conversion library (omi.key_conversion) that can load known formats and produce a valid OMI-format state dict (and vice versa), reducing the burden on frontends, trainers, and utilities.

In the future, we may collectively decide to adopt a true "packaged container" approach (like a zip with multiple sub-files), but the immediate priority is to unify key naming and metadata so that models can be more reliably shared in .safetensors format.

File Format & Metadata

At the highest level, an OMI-compatible model is a single .safetensors file containing:

  • A tensor dictionary with parameter data.
  • A metadata section holding JSON under the omi_data key.

This is an example metadata payload for a full (multi-part) model. In practice, many partial adapters—like LoRAs—will have fewer fields and different references. 


{
  "omi_data": {
    "schema_version": 1,

    // Optional. Describes the pipeline and how each sub-model is referenced.
    "pipeline": {
      // The pipeline type is one of a pre-defined set (e.g. "SDXL", "SD1.5", etc.).
      "type": "SDXL",

      "models": {
        // Each key identifies a component in the pipeline. The value can be
        // a string referring to the sub-model in this file (below in "models"),
        // or an object referencing an external file/URL by hash, if the component
        // is *not* included in this safetensors.
        "clip_l_tokenizer": {
          "model_type": "CLIP_L/TOKENIZER",
          "file_hash": "sha256:0xdeadbeef"
        },
        "clip_l": "clip_l",
        "unet": "sdxl_unet",
        "vae": "sdxl_vae",
        "clip_g_tokenizer": "...",
        "clip_g": "..."
      },

      // Optional free-form data about this pipeline.
      "info": {}
    },

    // The "models" dict enumerates each sub-model that *is* contained in this file.
    "models": {
      "clip_l": {
        "type": "CLIP_L/TEXT_ENCODER",
        "key_layout": "default",
        "hashes": {
          "content_hash": "sha256:0xdeadbeef"
        },
        "data": {
          // Optional data relevant to the sub-model. For instance:
          // "clip_skip": 2, or "prediction_type": "v".
        },
        "info": {}
      },
      "sdxl_unet": {
        "type": "SDXL/UNET",
        "key_layout": "default",
        "hashes": {
          "content_hash": "sha256:0x0000"
        },
        "data": {
          // E.g. "prediction_type": "eps"
        },
        "info": {}
      },
      "sdxl_vae": {
        "type": "SDXL/VAE",
        "key_layout": "default"
      }
    }
  }
}

Key-Naming Standard

The core principle is use the original model author's parameter names. This ensures that a derived model referencing those weights (e.g., a LoRA) can easily match them. Historically, some libraries replaced dots (.) with underscores (_) or split Q/K/V parameters differently. Going forward, we encourage:

  1. No forced replacement of . characters. Keep them unless you have a strong architectural need.
  2. If your model references multiple modules (e.g. text_encoder and unet) in the same safetensors file, you may add a prefix to avoid collisions—e.g. "unet.conv1.weight" vs "text_encoder.embedding.weight". In your metadata’s omi_data.models, you would define something like "unet" and all of that sub-model’s parameters are prefixed with "unet.".
  3. For partial LoRAs or other adapters, reference the underlying parameter name exactly, then append your LoRA suffix. See LoRA Naming below.

When distributing partial LoRAs or fine-tuned modules, the recommended approach is:

  • Maintain the original module’s param name. Do not rename it. If you only changed a couple of weights, just include those changed weights in your state dict. If you used LoRA, see the next section.
  • Include minimal references in your omi_data metadata to help a loader place these updated weights in the correct location. If the rest of the base model is needed, a loader can reference the base model by hash or path.

LoRA Naming

For LoRA parameters, the recommended standard is:

  • Use original_key_name.lora_down.weight, original_key_name.lora_up.weight, and optionally original_key_name.alpha.
    Example:
    unet.down_blocks.0.attentions.0.transformer_blocks.0.attn.q_proj.lora_down.weight
  • If a single safetensors file includes multiple modules (e.g., unet and text_encoder), then each module may have a unet. or text_encoder. prefix, but only if the base model’s parameters also use that prefix. In other words, the LoRA keys remain consistent with the base parameter naming, plus the .lora_down / .lora_up suffix.
  • No “global” replacement of . with _. We do not forcibly rename the original architecture’s parameters. The only additions are the .lora_down / .lora_up suffixes.

This scheme preserves direct alignment with the underlying architecture. If your training code internally modifies keys or splits Q/K/V into multiple parameters, you will need to convert them back to the “original model keys” when saving for public distribution under the OMI standard.

Reference Conversion Library

Because there are already many LoRA and partial-model variants in the wild, OMI will maintain a reference Python library omi.key_conversion that can:

  • Load known formats (Diffusers, older LoRA trainers, etc.).
  • Convert them to OMI’s recommended key layout.
  • (Optionally) Convert OMI-formatted safetensors back to one of those older formats.

This library only depends on PyTorch (for the state_dict reading/writing) and does not pull in large external dependencies. Community submissions to extend coverage for additional formats (such as new architectures, or new trainer quirks) are welcome.

Note that this does not automatically alter the model’s architecture. If the original trainer’s approach physically merges Q/K/V or otherwise changes shapes, a deeper transformation is required—the library includes some known transformation logic, but not every custom approach is guaranteed support.

Format for Full vs. Partial Models

The examples above describe a full, multi-submodel pipeline in a single .safetensors. However, OMI is equally applicable if you only want to distribute a single part (like a fine-tuned unet). In that case, you simply omit references to other pipeline components in omi_data. A loader can then link up the missing pieces from known base models, or load them from other .safetensors references by hash/path.

Looking Ahead: Packaged Container Format

In the future, OMI may formalize a single-file “bundled directory” approach, which physically includes multiple safetensors lumps (or multiple model shards) in one container file (akin to a zip or dduf). That would remove the need for “prefix” naming entirely. However, for the immediate future, the community consensus is to focus on:

  1. Standardizing key names to preserve direct architectural references.
  2. Using metadata to specify pipeline structure and hashes.

Once these pieces gain wide adoption, we can tackle a more comprehensive container-based standard and coordinate a broader ecosystem shift in tool support.

Hashing & Similarity

For omi_data references that point to external files, we recommend:

  • file_hash: a required sha256 of the entire external file. Allows direct file-matching.
  • content_hash: an optional additional signature that can be used to identify near-duplicates if the file has trivially changed. For example, OMI proposes hashing the first 4KB of each tensor (in alphabetical order of the keys).

These fields are flexible. Implementers can add more if desired, but the recommended minimum is a single sha256 for unambiguous referencing.

Conclusion

This proposal aims to solve the most pressing immediate problem: "parameter key mismatch" and "inconsistent naming" that break cross-compatibility. By settling on:

  • Original model author keys for base parameters.
  • Standard LoRA suffixes (.lora_down.weight, .lora_up.weight, .alpha).
  • Simple metadata in .safetensors (omi_data) to describe pipeline structure.
  • A reference Python library for bridging old formats.

…we can drastically reduce confusion and duplication of loading logic in the ecosystem.

— The OMI Working Group
